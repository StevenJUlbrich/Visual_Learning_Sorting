Spec-First Methodology

This page explains how 15 design documents and 81 locked decisions governed AI code generation throughout the project, and why this approach was necessary.

The Problem with "Vibe Coding"

The default way people use AI for code generation is conversational: describe what you want, let the model write it, iterate on the output. This works for small, self-contained tasks. It breaks down on anything with cross-cutting constraints.

A sorting visualizer sounds simple, but the constraints interact in non-obvious ways. The Insertion Sort generator must emit individual compare-then-shift tick pairs (never batched), the key-selection tick must use OpType.COMPARE for timing purposes but must NOT increment the comparisons counter, and the terminating compare must fire only when the loop exits by condition (not by j < 0).

The specifications exist to make misalignment detectable.

What Was Written Before Any Code

15 design documents covering product requirements, architecture, data contracts, UI layout, algorithm visualization, behavior, acceptance tests, test plan, dev environment, animation specification, CI pipeline, and animation foundation.

81 locked decisions in DECISIONS.md (D-001 through D-081), each resolving a specific ambiguity:

  • D-060: Each shift in Insertion Sort is an individual compare-then-shift tick pair. Never batched.
  • D-058: Heap Sort RANGE ticks must include the sift-down parent index in highlight_indices.
  • D-081: The View distinguishes Boundary T3 from Logical Tree T3 by message prefix, not contiguity.

The Two-Agent Workflow

Agent 1: Cowork (Opus) — The Architect

Loads full specification context. Designs prompts with exact code paths and exit gates. Makes architectural trade-off calls. Produces a prompt document for each phase.

Agent 2: Claude Code — The Builder

Receives the prompt and executes mechanically. Writes code, runs ruff check, runs pytest -x, reports pass/fail against exit criteria. Doesn't interpret — follows.

The Four-Step Prompt Pattern

  • DEVLOG PRE-ACTION — record the plan before execution.
  • IMPLEMENTATION — prescriptive prompt with code paths and gate commands.
  • GATES — mechanical pass/fail: lint, format, tests, AST parse, counter targets.
  • DEVLOG POST-ACTION — record what actually happened, surprises and corrections.
