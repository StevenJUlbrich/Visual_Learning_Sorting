Case 1The Duplicate-Value Blindspot

wiki/Misalignment-Case-Studies.md
SEVERITY · CRITICAL affected all four algorithms when the input array contained duplicate values · Phase 10c

SPEC What the spec required

compute_sprite_moves() must determine which sprites moved between two array states. Sprite identity tracked by unique ID, never by value — Critical Rule #1.

BUILT What was built

Value-delta detection:

changed = [i for i in range(len(old_state))
           if old_state[i] != new_state[i]]

DETECT How it was detected

Acceptance test AT-08 with array [3, 1, 3, 2, 1, 2, 3]. Algorithm sorted correctly — visual was wrong. Insertion Sort showed 1, 2, 3, 1, 2, 3, 3 instead of 1, 1, 2, 2, 3, 3, 3.

SWAP [0]↔[2] → old: [3,1,3,2] ≡ new: [3,1,3,2] → changed = []

FIX The fix

Added operation_type + highlight_indices as optional params. When changed is empty AND tick is SWAP/SHIFT with 2-element highlight → use highlight data to swap sprite IDs. Existing logic untouched for non-empty changed. +6 tests, backward compatible.

LESSON Why the spec mattered

The original implementation passed all 339 existing tests. The spec (Critical Rule #1) explicitly warned against value-matching, but the function was written during Phase 6c when duplicate arrays weren't yet testable. The spec caught the category of bug; the acceptance test caught the instance.

PRE-ACTION · PLAN

Augment compute_sprite_moves() with operation_type and highlight_indices (both optional, default None). When value-delta finds zero changes but tick is SHIFT/SWAP with 2-element highlight, use highlight data. Existing 8 Group 13 tests + 7 integration tests pass unchanged.

ROOT CAUSE

The list comprehension changed = [i for i in range(...) if old[i] != new[i]] produces empty list when equal values shift or swap. Function returns {} — no movement. Over a full sort with duplicates, sprites diverge from actual positions.
